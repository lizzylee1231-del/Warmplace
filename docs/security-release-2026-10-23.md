## 配置与发布顺序

1. 备份现有数据库数据与权限策略。给 Vercel 后端配置 SUPABASE_PUBLISHABLE_KEY，使用该项目的 sb_publishable_... key；保留原 SUPABASE_KEY，服务端 secret/service-role key 不得放入浏览器。
2. 在 Supabase Auth 中开启 Anonymous Sign-Ins。公开演示应配置认证速率限制；若开启 CAPTCHA，需先接入对应前端验证，不能只打开强制验证开关。
3. 用配套预览环境验收。前端的 /api 代理需要指向后端预览地址，不能混用旧后端；正式发布使用稳定后端地址。
4. 在受控窗口应用 supabase/migrations/20261023040432_secure_user_records.sql。迁移保留全部旧记录和 text 类型 user_id，增加幂等键及索引，用归属策略替换 allow all，取消无身份表访问，禁止 authenticated 直接物理删除。
5. 发布配套后端与前端并重新打开页面。旧版已打开页面会收到401，应刷新。可采用短维护窗口避免两个版本混用。

不要只合并一个仓库。不要为兼容旧版本而恢复无身份访问或公开 allow all。

## 旧记录边界

旧 user_... 设备标识可以伪造，不能作为认领记录的身份证明。升级后使用 Auth 分配的新 UUID。旧记录及本地旧标识保留，但不会自动合并。需要找回时，由项目所有者制定核验及人工迁移方案；本次没有删除或改写旧记录。

匿名会话清除或换设备后可能失去原记录访问能力，本版本没有永久账号恢复功能。前端隐私说明已据此更正，并说明服务端会保存上下文摘要、当前删除属于软删除。

## 验收

- /api/health 是存活检查；/api/ready 实际检查数据库，AI configured_not_probed 不是模型调用成功证明。
- /api/docs 可访问；所有业务接口无令牌401，伪造身份403。
- 两个会话互相不能读取、修改或软删除记录。
- 合成数据完成分析→保存→刷新读取→回顾/周信，同一 client_request_id 重试只保存一条。
- 写库失败明确503，模型失败返回 fallback 与 unknown，空记录没有虚构统计。
- 复查 Supabase advisors 和数据库策略。

验证依据：后端29项测试；前端7项测试、语法检查和打包；Postgres 回滚事务验证本人/他人/无身份隔离、禁止变更归属和幂等性；本地浏览器使用内存数据和模拟模型跑通记录到回顾。回滚后确认原策略仍在，测试列和记录均未保留。

真实线上AI和持久化验收需在生产发布获授权并完成配置后进行；本次未创建真实匿名账号，未调用付费模型。
